# Product Requirements — radargen

> **How to read this document.**
> **§§3–7 are normative.** Every requirement carries an ID (`FR-n`, `NFR-n`) and is written to be directly testable. Requirement text states *what* the tool does, not why.
> **§9 is the decision log.** It holds the reasoning — including options considered and rejected — so settled arguments don't get re-litigated. Decisions carry `D-n` IDs and are referenced from the requirements they explain.
> If §6/§7 and §9 ever disagree, **the requirement wins** and the decision log needs updating.
> **IDs are permanent labels, not positions.** A requirement added in a later revision takes the next free number and sits with the requirements it belongs beside, so IDs within a table are not always ascending. Renumbering would invalidate every cross-reference in §9 and §12 for no gain.

## 1) Summary

**`radargen`** (D-32) is a single-binary tool that reads a CSV of technology-radar entries and renders an interactive HTML radar page, plus PNG and SVG exports of the same visual. Two things distinguish it from the industry-standard renderer: an **arbitrary number of quadrants** rather than a hardcoded four, and a **configurable ring set** whose default is `--rings "Assess,Trial,Adopt,Retire"`. The flag is declared **edge-to-centre** (FR-12, D-60), the order a radar is read in, so that default is the lifecycle Assess → Trial → Adopt → Retire as written: Assess at the outer edge, Retire at the centre.

That default is the lifecycle an in-house radar actually tracks: a technology is evaluated, piloted, adopted as a standard, and eventually retired. It differs from the ThoughtWorks set (Adopt/Trial/Assess/**Hold**) because the two radars do different jobs. ThoughtWorks publishes advice to an industry it doesn't operate, so *Hold* is a caution about taking something up. An in-house radar governs an estate you actually run, where the harder question is what you're on the hook to remove — so *Retire*, a state with an owner and an exit date, earns the fourth ring more than *Hold* does. Either set works; `--rings` chooses (D-4).

It replaces the stock ThoughtWorks [build-your-own-radar](https://github.com/thoughtworks/build-your-own-radar) clone currently used as the interim renderer for an in-house technology radar.

A working layout prototype sits alongside this document: **`mockup.html`** in this folder. It is a validation artefact, not a reference implementation — see §10 for what it does and does not prove.

## 2) Problem / Motivation

A standards catalogue has a category (quadrant) count decided by what the organisation maintaining it actually does — not necessarily the four that ThoughtWorks defaults to (Tools / Platforms / Languages & Frameworks / Techniques). **The originating case for this tool is a three-category catalogue — Tool / Platform / Practice — at an IT outsourcer.** Stock BYOR hardcodes exactly four quadrants, so a three-category radar doesn't fit it without either padding to four with an unused category or forking the renderer.

Separately, a catalogue-derived CSV typically carries metadata the catalogue cares about — `domain`, `last_affirmed`, `exit_date`, survey notes — that BYOR silently ignores, because its schema only recognises `name, ring, quadrant, description`. That data already exists; nothing currently surfaces it.

A prior, more ambitious attempt (a Rust CLI + TOML catalogue, designed 2026-08-09) was deliberately rejected: it duplicated a full relational catalogue-and-decision-linking feature already specced in a separate tool (ArchMan, code **TSR**), where a radar entry → ADR reference becomes a real traversable relationship rather than an inert file path. This tool is scoped narrower on purpose — **a renderer, not a catalogue store** — so it doesn't reopen that objection. See §8 and D-1.

## 3) Goals

- **G-1** Render a technology radar from a CSV with **N quadrants** (N ≥ 1), not a fixed four.
- **G-2** Make the ring set and its order configurable, defaulting to `Assess,Trial,Adopt,Retire` edge-to-centre — the lifecycle Assess → Trial → Adopt → Retire, read from the outer edge inward — so the existing radar renders with zero configuration.
- **G-3** Give **Adopt — Default** and **Adopt — Conditional** a distinct visual treatment *within* the Adopt ring. Conditional adoption is a qualifier on the ring, not a fifth ring: the item genuinely is adopted, and what varies is whether it's the default choice or one permitted under stated circumstances. Promoting that to its own ring would misrepresent it as a lesser lifecycle stage.
- **G-4** Surface the catalogue metadata already present in the CSV (domain, rationale, last-affirmed, exit commitment) instead of dropping it.
- **G-5** Tolerate CSV content outside the core model — an unrecognised ring value or an unrecognised column never fails the render.
- **G-6** Output a **single self-contained HTML file** — no server, no build step to view it, safe to commit to the published-editions folder or email to a client.
- **G-7** Output a **PNG and an SVG** of the same radar + legend for slides, PDFs, print, and vector-editing tools — one shared visual, not two or three things to keep in sync.
- **G-8** Ship as a single compiled binary (Rust), consistent with the existing cargo-based toolbelt.
- **G-9** Make the shareable graphic **self-explanatory on its own**: it carries the edition's identity and a key to its own visual encodings, so a PNG pasted into a slide is not an unlabelled diagram of numbered dots. The HTML output can lean on a tooltip and a detail panel to explain itself; a static image has neither.

## 4) Non-Goals

- **Not a catalogue or decision-link store.** It does not hold ADR references as first-class, traversable relationships — that's ArchMan TSR's job. This tool's CSV can carry a decision-link column as inert text (a filename or URL), same as today.
- **Not a governance or policy-enforcement tool.** No enforcement of rules like "exactly one Default per domain"; at the scale a radar runs to, such rules are cheaper to check by hand. Note this is about *policy*: the tool does perform *structural* input validation (§6.1, §7) — it will refuse a CSV it cannot parse, and warn about values it cannot plot. That is parsing, not governance. A third, narrower case is likewise not governance: the tool may report a limitation of **its own rendering** — FR-88's notice that a high quadrant count will not read well — because that describes the output rather than judging the input.
- **Not a live/dynamic dashboard.** No database, no server process, no auth. Point-in-time render of a point-in-time CSV, matching how radar editions are already published (dated, immutable, successive).
- **Not reading a standards catalogue directly.** Input is a CSV, not a live scan of the catalogue's own source documents — that mapping stays a manual (or later, scripted) export step, kept separate from this tool's concern.
- **Not a print-styled web page.** See FR-52.

## 5) Users and Use Cases

| Persona | Side | Environment | What they need |
| --- | --- | --- | --- |
| **Radar maintainer** | Author | Command line | Publish a dated radar edition from a CSV in one command, and get a slide-ready image from the same source |
| **Engineer inside the organisation** | Reader | Desktop browser | Look up whether a technology is Adopt/Trial/Assess/Retire and *why* — the rationale and domain, not just the position. Under the curated semantics D-49 recommends, an **absent** item means "not featured this edition" rather than "not in use" |
| **External stakeholder** | Reader | Whatever they have, including a phone | Open an emailed HTML file, or read the radar in a slide deck, with no tooling installed |

**UC-1 — Publish an edition.** The maintainer exports the catalogue to CSV, runs the tool once for HTML and once for PNG, and commits both into the published-editions folder under a dated filename. The HTML diffs cleanly against the previous edition (NFR-4).

**UC-2 — Consult a published edition.** A reader opens the HTML file directly from disk or an email attachment, finds an item by scanning the legend or the radar, clicks it, and reads its rationale and last-affirmed date. No network, no server, no install (NFR-2, NFR-5).

**UC-3 — Reuse the visual.** The maintainer drops the PNG into a slide deck, or opens the SVG in Figma to restyle it for a house template, without needing the original CSV.

## 6) Functional Requirements

### 6.1 CSV input

#### 6.1.1 File-level parsing

| ID | Requirement |
| --- | --- |
| **FR-1** | Input is a single UTF-8 encoded CSV file, comma-delimited, quoted per RFC 4180. **A header that is a single column holding `;` or a tab is refused as another separator**, naming the separator and saying to export with commas — Excel writes `;` wherever a comma is the decimal mark (D-59). **A `;` or tab directly after a header field's closing quote**, spaces aside, is reported as that separator too, not as text after a quote, and the refusal never states a column count it did not see (D-65). |
| **FR-2** | A leading UTF-8 byte-order mark is stripped before parsing. *(Excel emits one by default; without this the first header reads as `﻿name` and FR-5 fails on a file that looks correct — see D-11.)* |
| **FR-3** | The first row is a header row. Header names are matched under the normalisation rule of FR-76, the same one applied to values. **A blank record is not a row**: one whose every field is empty or only whitespace and FR-76's format characters, other than the controls FR-90 removes — an empty line, a line of only spaces and tabs, a line holding only a stray byte-order mark left by concatenating two exports, or Excel's `,,,` for a cleared row (D-65). It is skipped wherever it sits, including above the header, so "first row" means the first non-blank record; its lines still count toward NFR-10's line numbers. Blankness is tested before FR-90's removal, so a field holding only an undisplayable character is not blank. A file with no non-blank record has no header and is a hard error naming FR-5's required columns (D-59). |
| **FR-76** | **One normalisation rule, applied to every value read from the CSV or from `--rings`** (including a `rings` array from `--config`, FR-91). Both operands of a comparison — header names (FR-3, FR-4), `quadrant` grouping (FR-9), `ring` against the declared list (FR-16, FR-63), `qualifier` (FR-20), `status` (FR-26), and duplicate-`name` detection (FR-28) — are trimmed at both ends of any mix of whitespace and **Unicode format characters** (general category Cf, such as U+FEFF or U+200B) other than the tag characters U+E0001 and U+E0020–U+E007F, and folded case-insensitively before comparison (D-61). **Folding means Unicode's default lowercase mapping** — locale-independent, the mapping Rust's `str::to_lowercase` implements — not full case folding and not any locale's rules. The **ordering** comparisons of FR-10 and FR-34 normalise the same way, so a stray leading space cannot sort an item away from the name it duplicates. **Every string ordering compares by Unicode code point** — on normalised values for FR-10 and FR-34's case-insensitive keys, on trimmed but unfolded values for the **ordinal** tiebreaks of FR-9 and FR-34 (D-63) — which is the same order as comparing UTF-8 bytes and differs from UTF-16 code-unit order above the BMP (D-53). A value **tested for emptiness** is likewise tested after trimming, so a field holding only whitespace or format characters counts as empty wherever emptiness decides behaviour (FR-4, FR-6, FR-7, FR-20's blank-vs-unrecognised split, FR-29, FR-63, FR-93). FR-3's blank-record test is the one exception: it reads the raw field, before FR-90's removal, and counts as blank only whitespace FR-90 does not remove and the format characters above that FR-90 does not remove (D-59, D-65). A value **parsed** is trimmed before parsing (FR-24, FR-25), which does not affect FR-24's rule that it renders verbatim either way. Normalisation never edits displayed text, with three exceptions, all of them FR-76's trim and none of them a change of case: FR-9's quadrant label; FR-15's declared ring name, which is what then appears as a band label and legend subheading; and an item's `name`, which is shown trimmed wherever it appears (D-76). Every other column is shown verbatim. Values that do not come from the CSV or `--rings` are outside this rule and state their own: the `-o` extension (FR-52), `--theme` (FR-56), and `--title`/`--subtitle`, whose empty-or-whitespace rule is FR-65's. |
| **FR-4** | A duplicate header name — duplicate after FR-76's normalisation, so `Name` and `name ` collide — or a row whose number of values doesn't match the header's number of columns, is a hard error (NFR-8) naming the 1-based line number. Mismatched rows are reported as one grouped line when there are several (NFR-20, D-62). Whether for one row or several, the message ends with the likely cause NFR-20 gives for what it saw. When the header has unnamed columns, the mismatched-row error says how many of its columns are unnamed — `the header's 5 columns, 1 of them unnamed`. **An empty header cell names nothing and is never a duplicate**, so Excel's trailing empty columns (`…,description,,`) pass (D-59); FR-93 drops the column it heads. |
| **FR-61** | An input path that does not exist, cannot be read, or does not decode as UTF-8 is a hard error. The decoding error names the 1-based line number where decoding failed and says what to do about it — re-save as UTF-8 — because the likely cause is an Excel export in a legacy code page, and "invalid utf-8 sequence" alone doesn't tell an author that (D-27). No transcoding is attempted and no encoding flag is offered. **A NUL byte is refused the same way**, naming its line: it is valid UTF-8, but no text file holds one, and its usual source is UTF-16 saved without a byte-order mark, which would otherwise pass as UTF-8 and fail every other row (D-65). |
| **FR-90** | **A character the output cannot display is removed, with a warning naming where it was: its line and column for a CSV field, or the flag (or `--config` key, with the file) for `--title`, `--subtitle` and a `--rings` entry.** That means a C0 control other than tab, line feed and carriage return, U+FFFE or U+FFFF, and also DEL and the C1 controls (U+007F–U+009F), which XML allows but no font draws, and the nine bidirectional embedding, override and isolate characters (U+202A–U+202E, U+2066–U+2069), which draw nothing and reorder the text after them (D-72). **Removal comes first**, before every other check reads the field: FR-6's emptiness test, FR-76's normalisation and FR-28's duplicate test all see the cleaned value. The one exception is FR-3's blank-record test, which reads the raw field so that a record holding only such characters is not skipped silently (D-59). So a `name` made only of such characters is empty, and `Kafka` followed by U+0001 duplicates `Kafka`, which is what the author sees in any editor that hides the character. Such a character decodes as valid UTF-8, so FR-61 does not reach it, but the output either cannot contain it (XML forbids it) or cannot draw it. Removing it once, on input, gives every format the same text (SC-7). Flag values follow the same rule as CSV fields because they reach the same output, and a flag is author text like any cell. For a `--rings` entry, removal also comes before FR-63's empty and duplicate checks. Replacing it was the alternative, and both candidates were rejected: U+FFFD has no glyph in FR-85's font, so the PNG would draw a missing-glyph box, and `?` would publish a mark the author never wrote. The warning keeps the removal from being silent. Repeated occurrences group into one line under NFR-20 (D-55). |
| **FR-97** | **A line break inside a quoted cell** (Excel writes one for Alt+Enter) **becomes one space in a label and a plain newline in prose.** Labels are the header names and the `name`, `quadrant`, `ring`, `qualifier`, `status`, `last_affirmed` and `exit_date` columns: every run of line breaks in one is a single space, applied before FR-76's trim and every match, so `moved` + line break + `in` is `Moved In`. Prose is `description`, `domain`, `rationale` and any other column: CR LF and a lone CR each become LF, so the detail panel and table can show the author's paragraphs. No warning: both are faithful to what the author typed. No carriage return reaches any output (D-79). |

#### 6.1.2 Required columns

| ID | Requirement |
| --- | --- |
| **FR-5** | The header **must** contain `name`, `quadrant`, `ring`, and `description`. A missing one is a hard error naming the column; when several are missing, one error names them all — `the header has no 'quadrant' or 'ring' column; …` (D-62). |
| **FR-6** | `name`, `quadrant`, and `ring` must be non-empty after trimming on every row (a blank record is not a row, FR-3). An empty one is a hard error naming the 1-based line number and the column. Empty values group per column under NFR-20 (D-62). |

| --- | --- | --- | --- |
| `name` | The item's name | Free text | Legend, detail-panel heading, marker hover tooltip |
| `quadrant` | Category — see §6.1.3 | Free text | Sector label, legend grouping |
| `ring` | Lifecycle position — see §6.1.4 | Whatever `--rings` declares | Radial position |

#### 6.1.3 `quadrant`

| ID | Requirement |
| --- | --- |
| **FR-8** | `quadrant` is free text. Whatever distinct set of values appears in the CSV becomes that render's quadrant set — no fixed vocabulary, no config key. |
| **FR-9** | Values are grouped under FR-76's normalisation, so `Tool`, `tool`, and `Tool ` are one quadrant, not three. Variants are compared **trimmed**, and the displayed label is the trimmed form of the **ordinally first** of them — a stable choice that does not depend on CSV row order (D-29). A quadrant written only as `Tool ` therefore displays as `Tool`. |
| **FR-10** | Quadrants render in **case-insensitive, locale-independent alphabetical order** (D-7), as FR-76 defines it. There is no override flag in this version — deferred rather than rejected (OQ-17). |
| **FR-11** | Near-duplicate names that FR-76's normalisation does not make equal — `Tool` vs `Tools` — are **not** normalised, merged, or flagged (D-8). |

#### 6.1.4 `ring`

Unlike `quadrant`, `ring` carries a meaningful order — a lifecycle progression — that cannot be inferred from the names alone. It is therefore declared explicitly rather than derived from the data (D-4).

| ID | Requirement |
| --- | --- |
| **FR-12** | The ring set and its order are declared by `--rings "<Name1>,<Name2>,…"`, **edge-to-centre**: the first entry is the outermost band, the last the innermost (D-60). |
| **FR-13** | Omitting `--rings` yields the default `Assess,Trial,Adopt,Retire` — the in-house lifecycle described in §1 — so a radar already using it renders with zero configuration. |
| **FR-14** | Ring count is N, matching whatever `--rings` declares, using the same equal-width-band geometry as any other count. `--rings "Hold,Assess,Trial,Adopt"` gives the ThoughtWorks convention, which ThoughtWorks lists centre-first as Adopt, Trial, Assess, Hold. **A consequence worth stating where the option is offered:** the innermost band has the least room — about a tenth of the outermost, since capacity follows the radius of FR-33's tracks — and this convention puts **Adopt** there. Whether that is a problem depends on what `Adopt` is being made to mean, which is the advice-versus-estate distinction §1 already draws. On an **advice** radar — ThoughtWorks' own use, "we think the industry should take this up" — Adopt is a curated recommendation list, deliberately short and re-chosen each edition, and the innermost band suits it. On an **estate** radar — "we have adopted this, it is in service" — Adopt is the standing catalogue and grows monotonically, which the innermost band cannot hold: about 2 items per quadrant at four quadrants against 10 in the second band from the centre. **The failure case is the cross**: estate semantics carried into the ThoughtWorks ring order, which is an easy mistake because the ring *names* are the familiar ones. The default set avoids it by putting the transient `Retire` at the centre and leaving `Adopt` in the second band from the centre. The tool does not object to any of this (§4); it warns per FR-89 when a band actually overflows, and OQ-16 would raise that innermost 2 to 8. |
| **FR-15** | Each comma-separated entry gets FR-76's trim, at its **ends only**, so `"Hold, Assess, Trial, Adopt"` and `"Hold,Assess,Trial,Adopt"` parse identically, while a multi-word ring name keeps its internal spaces. |
| **FR-63** | The declared list must yield **at least one** ring, with **no empty entry** (`"Adopt,,Trial"`) and **no duplicate** after the same trim-and-fold used for matching (`"Adopt,adopt"`). Each violation is a hard error naming the offending entry. A duplicate would make FR-16's match ambiguous and FR-32's band order undefined; an empty entry would draw a nameless band. Neither can be resolved by guessing what the author meant. |
| **FR-16** | A row's `ring` is matched against the declared list under FR-76, both sides normalised. |
| **FR-17** | A `ring` value outside the declared set is **not an error**. The row is omitted from the polar plot (there is no band for it), included in the table view flagged `not on the radar`, and a warning is emitted **naming the ring set's source** (D-61): `not declared by --rings`, `not declared by the rings key in radar.toml` for a `--config` file, named as given on the command line (FR-91), or `not one of the default rings` (FR-13). **The warning lists the declared rings and says how to plot the row** — add the value to the ring set's source; for the default set, pass `--rings` listing every ring wanted, since it replaces the default set rather than adding to it — so a typo such as `Adpot` shows beside the ring it missed (D-64). Exit code stays 0 (D-5). |
| **FR-18** | Unplotted rows are **not numbered and get no legend entry**. Item numbers remain contiguous across plotted items only. |
| **FR-19** | An empty declared ring — one with no matching rows — still renders its band, label, and circle. |

#### 6.1.5 Optional columns

All are optional. FR-29 governs what happens when one is absent or empty.

The link opens in a new tab (`target="_blank" rel="noopener noreferrer"`), says so to assistive technology, and its text is the address as written, trimmed. **Any other non-blank value is shown as plain text, never as a link, with a warning**, so a `javascript:` or `data:` address cannot become something a reader clicks (D-77). Blank or absent: no link (FR-29). | ID | Requirement |
| --- | --- |
| **FR-27** | Unrecognised columns are ignored, not an error. A column whose header cell is empty is not one of them; FR-93 governs it. The same CSV that feeds BYOR today keeps working unmodified, and a team may carry any extra column it finds useful (a revisit date, a survey note, a ticket reference) without the tool knowing about it in advance. |

#### 6.1.6 Example CSV

Three of the ten columns are matched against a known set of values, normalised per FR-76 — though `ring`'s set is whatever `--rings` declares, and FR-17 tolerates values outside it. Everything else is free text.

```csv
name,quadrant,ring,description,qualifier,domain,rationale,last_affirmed,exit_date,status
Terraform,Tool,Adopt,"Declarative infrastructure-as-code tool for provisioning cloud and on-prem resources.",default,Infrastructure as Code,"Default IaC tool across all managed environments.",2026-06-01,,No Change
Pulumi,Tool,Adopt,"Infrastructure-as-code authored in a general-purpose language instead of a domain-specific syntax.",conditional,Infrastructure as Code,"Acceptable where a client mandates a general-purpose language over HCL.",2026-06-01,,New
Ansible,Tool,Trial,"Agentless configuration management and orchestration over SSH.",,Configuration Management,"Bounded trial on one managed estate; was Assess last edition.",2026-05-12,,Moved In
Chef,Tool,Retire,"Agent-based configuration management using a Ruby DSL.",,Configuration Management,"Superseded by the Ansible trial outcome; migration owned and scheduled.",2026-03-15,2027-01-31,
Kubernetes,Platform,Adopt,"Container orchestration platform for deploying, scaling, and managing containerised workloads.",default,Container Orchestration,"Default for all new containerised workloads.",2026-06-01,,
Trunk-Based Development,Practice,Adopt,"Developers integrate small, frequent changes into a shared trunk.",default,Delivery Practice,"Default branching model for managed delivery teams.",2026-06-01,,
Legacy Ticketing-Driven Change,Practice,Rejected,"Manual, ticket-driven change approval replacing automated policy gates.",,Operations Practice,"Declined during the 2026 review — see the domain ADR.",2026-01-10,,
```

The last row (`ring = Rejected`) exercises FR-17/FR-18: not a declared ring, so it is skipped from the graphic and flagged in the table view rather than failing the parse. Every optional column is left empty at least once, exercising the "absent means don't render that field" behaviour.

### 6.2 Rendering

| ID | Requirement |
| --- | --- |
| **FR-30** | Quadrants are equal angular sectors; sector count derives from the distinct `quadrant` values present (FR-8). |
| **FR-31** | The 12 o'clock position, where ring labels sit, is aligned to a quadrant **divider**, never to a sector's centre. Since markers are always inset from a divider by a fixed angular margin (FR-33), this guarantees no marker can ever coincide with a ring label, at any quadrant count. |
| **FR-32** | Ring bands are equal-width radii, in the order `--rings` declares: the first declared ring is the outermost band and the last the innermost (FR-12). Band count derives from the declared ring count — N bands, not a fixed four. **Band widths are fixed by the ring count alone and never by how many items a ring holds** — a crowded ring does not grow at a sparse one's expense (D-47). |
| **FR-77** | **Start angle and rotation direction.** Quadrant dividers sit at `-90° + i × (360 / N)` for `i` in `0..N`, measured in SVG coordinates where 0° is 3 o'clock and angle increases **clockwise** on screen. Divider 0 is therefore at 12 o'clock, satisfying FR-31, and the quadrant **first** in FR-10's order occupies the sector immediately **clockwise** of it, with successive quadrants following clockwise. Without this, FR-31 pins a divider without saying which quadrant follows it or which way the order runs — six valid layouts at N=3, all satisfying every other requirement (D-36). |
| **FR-33** | Within a quadrant+ring band holding `n` items, item `j` (0-based, in the FR-34 order that numbers them) is placed at angle `quadStart + sector × (0.08 + ((j + 1) / (n + 1)) × 0.84)`, where `quadStart` is the band's opening divider per FR-77 and `sector` is `360 / N`. The **8% inset at each end** is a proportion of the sector, not a fixed angle, so it scales with quadrant count; at N=1 the single divider is both edges and the inset applies to each side of the full 360° span, leaving a visible gap at 12 o'clock. Radial position is `inner + (outer - inner) × (0.38 if j is even else 0.68)` — **alternating by index parity, never by a PRNG**, which would break NFR-4. Legibility degrades as items per band grows; markers **overlap rather than being dropped, shrunk, or capped**, and the band's items stay fully listed in the legend and the table view, which is where a crowded radar is read (FR-89, D-48). This is not an error condition (D-36). |
| **FR-34** | Items are numbered sequentially, ordered by **quadrant** (FR-10), then **ring in the declared order**, which is the order the legend presents (FR-35) — then **`name` case-insensitively, locale-independently**, then `name` **ordinally**, trimmed (FR-76) — the FR-9 tiebreak, so two names differing only in case do not fall through to row order the way D-29 stopped them doing for labels — then CSV row order as a last resort. Numbering follows presentation order so that a quadrant's numbers **ascend as the reader scans down its legend group** (D-33). The tiebreak chain is fully specified because output determinism (NFR-4) depends on it. |
| **FR-35** | A side legend maps number → name, grouped by quadrant and sub-grouped by ring, with rings in the **declared** `--rings` order — edge-to-centre, which for the default set is lifecycle progression, earliest stage first. The rule is positional, not semantic: it follows whatever list is declared without reading meaning into ring names (FR-21, D-4, D-60). This order is the one FR-34 numbers in, so a quadrant's numbers ascend as the reader scans down its group. Each quadrant group carries a **swatch in that quadrant's colour** (FR-67) beside its heading — the one place the colour→quadrant mapping is stated in words, which is why FR-66 leaves quadrant colour out of the key. The three levels — quadrant, ring, item — are distinguished by **indentation as well as type style**, each stepped in under the one above. Weight and letter-spacing alone leave the levels reading as an alternating flat list, which is what makes a long legend hard to scan. |
| **FR-74** | A legend row carries the number, the name, and — **inline after the name**, not on a line of its own — whichever of `qualifier` and `status` are present — `No Change` excepted, which FR-40 draws as the plain marker and no row shows (FR-50). The **ring is not repeated on the row**: it is already the subheading the row sits under, and restating it on every row is noise that costs a line's height across the whole legend. Where the trailing text does not fit beside a wrapped name it takes its own line rather than being truncated. **The inline trailing text continues the name's own text**, after a no-break space, so a reader's text spacing pushes it along rather than running the name into it (D-78). |
| **FR-75** | The row's **accessible name still carries the ring**, even though the visible row does not. Grouping conveys the ring to someone reading the legend as a shape; it conveys nothing to someone arriving at a single row via Tab or a screen reader's control list, where FR-50 requires the label to state the item's position. Visual de-duplication must not become an information loss in the accessibility tree. |
| **FR-36** | Hovering a marker shows its number and name as a native tooltip (an SVG `<title>`). A number on a dot is not identifiable without it. |
| **FR-37** | Hovering a marker highlights its legend row, and vice versa — **on hover, not only on click**. Scanning a long legend to match a numbered dot is real friction at the item counts a mature radar accumulates. |
| **FR-38** | Clicking a marker or legend row opens a detail panel showing `description` plus whatever optional-column data is present. Clicking the same target again, pressing Escape, or using an explicit close control closes the panel **and** clears the selection. There is no state where a panel is open but nothing indicates why, and no state the user cannot return to nothing-selected from. |
| **FR-72** | **Selection is indicated on the marker *and* the legend row, whichever of the two was activated** — the relationship is symmetric, so the indication must be. Selecting from the legend without marking the marker leaves the reader unable to tell which of N numbered dots the open panel describes, which is the question the legend exists to answer. |
| **FR-73** | The selected state is **visually distinct from the hovered state** on both marker and legend row, since the two can apply to different items at once. Selection is **not** drawn as a ring around the marker: rings already encode `status` (FR-40), and a second concentric ring would be read as one. |
| **FR-67** | Each quadrant takes the palette entry at its **index in the sorted quadrant order** (FR-10), cycling from the start when quadrants outnumber palette entries. Colour is therefore a function of the quadrant names alone, which is what makes it reproducible across runs and machines (NFR-4). Repeated colours at high quadrant counts are tolerable only because of FR-39. |
| **FR-81** | **The built-in palette has eight series entries, in this order:** `#0072B2` blue, `#C25400` vermillion, `#00857A` teal, `#787832` olive, `#B5476B` rose, `#2F9626` green, `#C431B8` magenta, `#9D5A43` terracotta. The **order is normative, not just the set**: FR-67 assigns by index, so a three-quadrant radar uses only the first three, and the list is arranged most-separable-first so that every prefix is itself a good palette. Series values are **shared by both built-in themes**; only the neutral roles differ (FR-82). Ships as `docs/product/palette.sample.css`, which doubles as the `--palette` starting point §6.6 promises; `palette-proof.html` in the same folder carries the verification (§10). |
| **FR-82** | **The remaining colour roles**, which `--palette` may also override: `--surface-1` (radar ground), `--surface-2` (legend, detail panel, table), `--text-primary`, `--text-muted`, `--stroke-ring`, `--stroke-divider`, `--marker-hollow` (FR-20's conditional fill, which is the surface behind the marker), and `--focus` (FR-48's indicator). Light: `#FFFFFF`, `#F4F5F7`, `#16191F`, `#585F6B`, `#7E858F`, `#848B96`, `#FFFFFF`, `#0B5FA5`. Dark: `#15181D`, `#1E222A`, `#E8EAEE`, `#A6AEBB`, `#6C7480`, `#666E7A`, `#15181D`, `#7FB8E6`. Every value is verified against SC-17: series entries and strokes clear **3:1** on both surfaces of their theme, text clears **4.5:1**. Ring circles and quadrant dividers take the 3:1 rule rather than being treated as decorative, because they are what make a band or sector readable as a region. **A number drawn on a solid marker or legend badge takes, per series entry, whichever of `#FFFFFF` and `#16191F` contrasts more with that entry**, decided when colours are bound rather than listed as a role, so it covers a `--palette` file's entries as well as the built-in eight. No single ink serves all eight: white on FR-81's green is 3.81:1, short of the 4.5:1 text floor, and `#16191F` falls short on all seven of the others. Chosen per entry, the built-in eight take white except green, which takes `#16191F`, and the lowest ratio is teal's 4.53:1 (D-54). |
| **FR-83** | **Palette separability degrades along the list, and this is a stated bound rather than a defect.** Minimum pairwise perceptual distance, normal vision / colour-vision deficiency: entries 1–3, ΔE 49.2 / 12.9; 1–5, 46.6 / 11.8; 1–7, 42.1 / 8.2; 1–8, 32.1 / 8.2. Eight is the ceiling because one colour set clearing 3:1 on **both** themes is confined to relative luminance 0.12–0.30, and within that band dichromats have roughly one usable hue axis — so no ninth entry exists that is distinct to both normal and deficient vision (D-41). Past eight quadrants FR-67 cycles, so a colour repeats — but **not usually on adjacent sectors**. Because the last sector and the first are neighbours around the circle, a repeat lands on an adjacent pair only when the quadrant count is **one more than a multiple of eight** (9, 17, …); at 10 through 16 the repeats are separated by at least one other colour. That makes **N=9 the worst case**, which is the count D-41 chose eight entries to push the problem out to. FR-39 keeps either case legible rather than ambiguous. No warning is emitted — that would be the governance behaviour §4 rules out. |
| **FR-85** | **The pinned font is Inter, as two static instances — Regular (400) and SemiBold (600) — subset to Latin, Latin Extended, Vietnamese, Greek and Cyrillic (Google Fonts' `latin`, `latin-ext`, `vietnamese`, `greek` and `cyrillic` ranges, with their `-ext` ranges where Inter draws them) and vendored pre-subset.** Chosen for FR-70's constraint rather than for taste: the narrow arrangement puts 12.5px legend text on a phone and SC-6 asserts it stays legible, which is the brief Inter is designed against (large x-height, open apertures). Licensed **OFL-1.1**, which grants the redistribution NFR-7 needs and the embedding NFR-5 needs; the licence text ships beside the font files. Three qualifiers are load-bearing. **Static, not variable** — a variable font's metrics depend on axis coordinates, so a browser and `resvg` resolving an axis differently would reintroduce exactly the HTML-versus-PNG divergence FR-84 closes (D-43). **Two weights** — FR-35 separates the legend's three levels by indentation *and* type style, which two weights plus size and letter-spacing cover; every additional weight is bytes inlined into every published edition (NFR-5). **Subset once and vendored, not subset at build time** — a build step is one more thing that can differ between machines, which NFR-4 does not tolerate. **Latin Extended, not Latin-1 alone** — `latin` stops at Latin-1, so a Czech, Polish, Hungarian, Baltic or Turkish name would draw a missing-glyph box in the PNG while the browser fell back to a system font, breaking SC-7's parity with no warning; the extended range roughly doubles the inlined WOFF2 pair, from about 62 kB to about 117 kB (D-43). **Vietnamese, Greek and Cyrillic as well**, because Inter already draws them and they cost only bytes, which the regenerated subset measures; scripts Inter does not draw stay out (A-4, D-68). |
| **FR-86** | **A `--palette` file must define every colour role of FR-82 — all eight — or it is a hard error naming the missing role.** **Every value, roles and series entries alike, is a `#RRGGBB` hex colour** (case-insensitive), the form `palette.sample.css` uses. Anything else is a hard error naming the role, because FR-82's marker-number ink is computed from the value's luminance and cannot be computed from `rgb()`, a named colour or `#RGB` without a CSS colour parser the tool does not otherwise need (D-54). Partial definition is not filled in from the built-in palette: mixing a custom surface with a built-in text colour silently produces the contrast failure NFR-1 already disclaims responsibility for on custom palettes, and the author would have no way to see which colours came from where. This is the structure-is-fatal line of NFR-9 applied to a file rather than a row (D-44). |
| **FR-87** | **A `--palette` file's series entries are a list, not a fixed count.** It must define `--series-1`, and may define as many further entries as it likes, **numbered contiguously**; the count it declares is the palette size FR-67 cycles over. Five entries give a five-colour palette, twelve give a twelve-colour one. A **gap** (`--series-1`, `--series-2`, `--series-4`) is a hard error naming the missing index, since it cannot be told from a three-entry list with a typo. A single entry is legal and renders every quadrant in one colour — FR-39 keeps that readable, and §4 rules out warning about a choice the author may have meant. The free count is a **consequence of the file being a list**, not a feature offered for its own sake: a custom palette serves one theme and so has roughly twice the usable luminance band, but **more than eight quadrants is a taxonomy problem the renderer should not be read as endorsing** (A-5). Nine or more entries are accepted without comment — §4 rules out warning about it — and are not the recommended answer to a crowded radar. |
| **FR-88** | **A quadrant count above six emits one warning naming the count**, then renders normally (exit 0). It fires **once per render, not per row**, and is the tool reporting a limitation of **its own output** — sectors narrow, labels crowd a single circle with no collision rule (OQ-14), and past eight FR-67 begins cycling colours. It is **not** a judgement about the author's taxonomy, which is why it warns rather than refuses and why there is no cap and no `--force`. Six is the threshold because three to six is the range the geometry is comfortable at (A-5), and because a threshold worth warning at has to be defensible — items-per-band has one too, computed rather than assumed (FR-89). Ordering: this warning concerns the render as a whole and carries no CSV line, so it is emitted **before** the line-ordered row warnings, keeping NFR-11's order total. |
| **FR-89** | **A band holding more items than fit without overlapping emits one warning naming the quadrant, the ring, the count, and how many fit.** Capacity is computed, not guessed: the largest `n` for which FR-33's placement leaves no two markers closer than one marker diameter — a deterministic function of quadrant count, ring index, ring count and radius. Capacity is evaluated at the wide arrangement's scale; in the narrow arrangement markers are relatively larger (D-69), so a band can overlap there before it reaches capacity. It is evaluated against the **plain** marker footprint, FR-40's status rings being the minority case, so a band full of `New` items may overlap without warning; the threshold is a floor and the message says how many fit *comfortably* rather than claiming precision it does not have. One warning per overfull band, not per item. **Overlap is then the behaviour** — markers are not dropped, shrunk, moved to another band, or capped, since each of those misplaces or hides an item the CSV asserts (D-48). |
| **FR-39** | **Quadrant identity never depends on colour alone.** Angular position and the sector-edge label always disambiguate an item's quadrant, independent of whether that quadrant's colour is distinguishable at a glance. Necessary once quadrant count exceeds the 3–4 colours that read reliably on their own — and once FR-67 starts reusing them. |
| **FR-40** | `status` is drawn on the marker itself, following the original ThoughtWorks convention rather than an icon or colour badge: **New** — a full ring around the marker; **Moved In** — a half-ring on the side facing the radar's centre; **Moved Out** — a half-ring on the side facing the outer edge; **No Change** or absent — the plain marker. |
| **FR-41** | A plain HTML table of every item is available as a toggle — the non-visual fallback, the only way to see unplotted rows (FR-17), and the easiest way to eyeball the whole dataset at once. Unplotted rows are visibly flagged **`not on the radar`** — the words FR-17 and the accessible name use, so the flag a sighted reader sees is the one a speech-input user can say (WCAG 2.5.3, D-66) — not silently interleaved. |
| **FR-78** | **The table carries one row per CSV data row** — plotted and unplotted alike — with a column for the item number (**empty for unplotted rows**, which FR-18 gives no number), `name`, `quadrant`, `ring`, and then **every other named column in the header, `description` included**, in header order (D-80). Absent columns get no column; empty cells stay empty per FR-29. Plotted rows come first in FR-34's order, then unplotted rows in CSV order, under a visible flag rather than interleaved. **Table rows are activatable as legend rows are**, through a button in the name cell (FR-38, FR-48, FR-50), opening the same detail panel — this is the *only* route to an unplotted row's panel, since FR-18 gives it no legend entry and no marker to click (D-38). The detail panel is built from the item's table row, so each item's prose is in the page once (D-80). |
| **FR-42** | A CSV with **zero data rows** (headers only) renders a valid empty state — ring circles, no quadrant dividers or labels — not a divide-by-zero or a crash. Since `quadrant` is required on every row that exists (FR-6), this is the only input shape where quadrant count reaches zero. A CSV whose rows are **all unplotted** (FR-17) is a different shape and not an empty state: sectors, dividers, and labels render from the quadrants those rows carry, the graphic simply holds no markers, the legend renders its quadrant groups empty (FR-18 gives unplotted rows no entry), and every row surfaces in the table view. With no quadrants at all the legend is omitted, as the title is when it is empty. |
| **FR-43** | Quadrant counts of **1 and 2** render correctly: N=1 draws a single divider at 12 o'clock with one full-circle sector; N=2 draws two dividers. Neither is a special case in the geometry. |

### 6.3 Radar, legend, and key as one SVG document

| ID | Requirement |
| --- | --- |
| **FR-44** | The radar, the legend, **and** the key (FR-66) are authored as a **single self-contained SVG document**, not an SVG radar beside an HTML legend. This is what makes PNG export cheap instead of requiring a full HTML/CSS rendering engine (D-14). |
| **FR-65** | `--title <text>` and `--subtitle <text>` render into the shared document above the radar, so every output format carries the edition's identity (G-9). Both are optional and independent: an omitted flag renders **nothing at all** — no placeholder, no reserved blank space, and the block below moves up. Neither value is derived from the output filename, the CSV, or the clock (D-24). Either may contain `{edition}`, which expands from the author's `--edition` (FR-92). **An empty or whitespace-only value counts as omitted** and renders nothing; on the command line it is how a value from `--config` is suppressed (FR-91). With no title, the HTML page's tab title and a visually hidden level-1 heading read *Technology Radar*, so the page still has a name and an outline; the drawn document is unchanged (D-75). |
| **FR-66** | The shared document includes a **key** to the marker encodings the reader cannot otherwise decode: hollow versus solid (`qualifier`, FR-20) and the three `status` treatments (FR-40). The key names each encoding in words beside a sample marker drawn the same way the radar draws it. It is rendered **whenever the radar is** — a fixed block, not one that varies with which encodings this dataset happens to use (D-25). Quadrant colours are not part of the key; the legend already groups by quadrant with a colour swatch, and FR-39 means colour is never load-bearing anyway. |
| **FR-45** | The HTML output embeds this document; SVG export writes it out directly; PNG export rasterises it. **One layout engine, two arrangements (FR-68), three output modes** — not separately-maintained renderings. Every format's graphic comes from the same code path; what varies between arrangements is where the blocks are placed, and what varies between formats is which arrangement is written out (FR-71). |
| **FR-46** | Long item names are **wrapped, not truncated** — the generator measures text and line-breaks into multiple `<tspan>`s itself. Full names matter more on a shareable static graphic than they would on an interactive page where a tooltip could cover for a truncated label. |
| **FR-79** | **The wrap is greedy first-fit, against a fixed maximum column width.** Words are taken in order and placed on the current line while they fit; the first that does not starts a new line. Greedy is chosen over a balanced algorithm because it is trivially deterministic and reproducible in any language — SC-7 asserts that HTML and PNG wrap at the same points, so the algorithm is part of the contract, not an implementation detail (D-39). A **single token wider than the column is broken mid-token** at the last character that fits and continued on the next line: FR-46 forbids truncating it, and the alternative — letting it overflow — would push it outside the `viewBox`. The legend column has a **fixed maximum width**, **one value for both arrangements**: the narrow document's width less its margins, so a legend wraps at the same points wide and narrow (D-56). Its rendered width is the lesser of that maximum and the longest measured line, so the document does not reserve space it never uses. The radar's quadrant and ring labels **do not wrap** — they are placed on one line at any length. The legend's headings are not radar labels and wrap at the column like names, with a hanging indent: a heading wider than the column less its indent continues on further lines at that same indent. A quadrant name is centred on its sector's middle angle and **pushed outward along it** by half its width × \|cos θ\|, so its inner end sits on the label circle's tangent at the label point (300 units out) — on the circle at 3 and 9 o'clock, beyond it elsewhere — whatever its length, and at any radar scale above about 0.3 a long name never crosses the outer ring (D-70). Below that scale a 6 o'clock label touches the ring's stroke whatever its length, a bound that predates the push. Label collision at high quadrant counts is accepted on the same terms as FR-33's marker crowding, not treated as an error. **Fit is judged at the layout width** (D-78): the shaper's advance plus WCAG 1.4.12's allowance, so a line that fits stays fit when a reader spaces the text out. |
| **FR-84** | **Text is measured through the same shaper that rasterises it.** `resvg` lays out text with `harfrust`; the generator measures with `harfrust`, at the version `resvg` resolves, over the same face, so FR-79's wrap points and FR-46's line breaks agree with the rasterised output **by construction rather than by coincidence** (D-67). Summing raw `hmtx` advances is **not** sufficient and is specifically ruled out: it drops GPOS kerning, diverging by up to 2.2% of a string's width — enough to move a wrap point, in either direction, and zero on strings that happen to carry no kerning pairs, so the error cannot be corrected by a constant and does not show up in a careless sample (D-42). **Letter-spacing is not the shaper's job** and is added by the generator as `n-1` gaps, `n` being the number of shaped clusters — a combining mark that stays a separate glyph shares its base's cluster, as `resvg` applies spacing (D-67). **Sizes and wrap points add 1.4.12's allowance on top of the shaped advance** (D-78); positions where text continues other text use the advance alone. |
| **FR-47** | `<foreignObject>` must **not** be used. See D-15. |

**Scope boundary — what is inside the shared SVG:** the title block (FR-65), the radar circle, its markers, the legend, and the key (FR-66) — the "shareable graphic" a PNG must reproduce. The detail panel and table-view toggle are auxiliary HTML/CSS/JS chrome around that graphic, present in the HTML output only — a static image has no interactive drill-down to reproduce.

**Consequence, accepted — per-item prose is HTML-only:** the per-item prose — `description`, `domain`, `rationale`, `last_affirmed`, `exit_date` — reaches the reader **only through the HTML output's detail panel and table view**. PNG and SVG carry the graphic, not the write-ups. This is deliberate rather than an oversight (D-26): rendering every item's prose into the shared document would make a forty-item edition's PNG mostly text, and would load the riskiest part of the build (text measurement, R-1) with the work least worth its cost. The formats divide by job — the image is for *showing* the estate's shape, the HTML for *consulting* it (UC-2 versus UC-3). SC-7 is scoped to match.

**Consequence, accepted — no inner scroll:** the legend has **no independent inner scroll**; the page scrolls as a whole. SVG has no equivalent of `overflow-y: auto` for arbitrary content. Nobody has asked for independent-panel scroll as a requirement — it was an artefact of prototyping in HTML, not a stated need.

### 6.4 Accessibility and responsiveness

| ID | Requirement |
| --- | --- |
| **NFR-1** | The HTML output targets **WCAG 2.1 AA**. **WCAG 2.2's target-size criterion (2.5.8) is claimed as well**, through FR-94 (D-66). **Text spacing (1.4.12) is met by construction** (D-78): layout reserves the room spaced text needs, so nothing overlaps or is clipped. The table view (FR-41, FR-78) is a fallback for the *data*; it does not by itself make the interactive radar accessible, which is what FR-48–FR-50 are for. **The claim is scoped to the built-in themes.** Supplying `--palette` replaces the colours with ones the tool did not choose and does not validate (§6.6), so contrast under a custom palette is the author's responsibility and the AA claim does not travel with it. Stated here because NFR-1 read as unconditional while §6.6 disclaimed exactly this — one of them had to give, and it is not the one the tool can enforce. **The 2.5.8 claim is scoped the same way to narrow documents up to 480 units wide** (D-71): a dataset whose quadrant names widen the narrow arrangement past that does not carry it, and FR-95 tells the author. |

| **FR-48** | Markers and legend rows are keyboard-operable: reachable by Tab, activated by Enter or Space with the same behaviour as a click, with a visible `:focus-visible` style on both. | **FR-49** | Escape closes the detail panel and returns focus to the element that opened it. |
| **FR-50** | Markers and legend rows are exposed to assistive technology as interactive controls: `role="button"` with an `aria-label` carrying number, name, and **whichever of `qualifier` and `status` the legend row shows** (FR-74) — `No Change` is shown nowhere, being FR-40's plain marker, so it is absent from the name and the name holds exactly what the row shows — then position (quadrant and ring, per FR-75) — so a screen-reader user exploring the radar hears what FR-66's key explains, and the visible row text is in the name (WCAG 2.5.3). The "or a native interactive element" alternative earlier drafts offered is **struck for them** — `<button>` has no meaning inside an SVG, and FR-47 rules out the `<foreignObject>` that would be needed to embed one, so it named an escape hatch the graphic cannot reach. **Table rows are outside the SVG, so the argument does not hold there:** they stay native `<tr>` and `<td>`, keeping the row and column-header navigation that makes FR-78's cells readable, and the name cell holds a native `<button>` named by the visible name and, for an unplotted row, the visible `not on the radar` flag. `role="button"` on the `<tr>` would replace every cell with its label and leave the optional columns unreachable from the view FR-41 calls the non-visual fallback (D-66). **Every control states whether the panel is open for it:** `aria-expanded="true"` on the control that opened the panel while it is open and `"false"` on every other, with `aria-controls` naming the panel (WCAG 4.1.2). The state stays out of the accessible name. |
| **FR-94** | **Every control's target is at least 24 by 24 CSS pixels at every rendered width down to 320 CSS pixels** (WCAG 2.2, 2.5.8). A legend row's height meets it at the smallest scale either arrangement reaches in that range, the narrow arrangement at 320 pixels included. A marker meets it through an invisible hit area centred on the marker, counter-scaled in the narrow arrangement as FR-70 counter-scales labels, so the drawn marker is not enlarged by it. Hit areas overlap wherever two markers' centres are closer than twice the hit radius — in most bands below FR-89's capacity, and in the narrow arrangement nearly always. They are drawn below every marker, so a visible marker always takes its own pointer events, and a hit area only fills empty space; where hit areas overlap each other, a marker there relies on 2.5.8's *equivalent* exception, since its legend row opens the same panel. The table's buttons are HTML and meet it directly (D-66). **This holds for a narrow document up to 480 user units wide**, which is as far as D-71 sizes rows and hit areas for; a dataset whose narrow arrangement widens past that falls short at 320 pixels, and FR-95 says so. |
| **FR-95** | **A narrow arrangement wider than 480 user units emits one warning naming the label whose width sets the radar's width, a quadrant's or a ring's**, then renders normally (exit 0). It fires once per render and, like FR-88, is the tool reporting a limitation of its own output: the radar could not fit the narrow column at the least scale it is drawn at (D-71), so the narrow document widened past the width FR-94's targets are sized for, and on a 320-pixel screen legend rows and marker targets render below 24 pixels and legend text smaller than at 480. The fix is a shorter name for the label that sets the width, which is not always the longest name (a label at 6 o'clock reaches less far than one on a diagonal), and is why the warning names it. A ring name sits across the vertical axis and widens the radar too, so a long `--rings` entry can set the width with every quadrant name short, or with no quadrants at all; the warning then names the ring and its source (D-73). It concerns the render as a whole and carries no CSV line, so it is emitted before the line-ordered row warnings (NFR-11). |
| **FR-80** | The HTML output sets `<html lang="en">`. WCAG 3.1.1 is a **Level A** criterion, so NFR-1's AA target already entails it, and nothing else in the document required it. The value is fixed rather than derived or flagged: A-4 already bounds entry text to scripts the pinned font draws, none of them right-to-left, and a flag for it would be configuration nobody has asked for. |
| **FR-51** | The HTML output is usable down to a phone-width viewport with no horizontal page scroll. Each arrangement scales fluidly (`width: 100%; height: auto` over its computed `viewBox`). The **wide** arrangement is shown above the breakpoint and the **narrow** one below it, selected by a CSS media query on `display` (D-16, FR-69). |
| **FR-68** | The generator emits the shared document in **two arrangements** from one layout engine: **wide**, with the legend beside the radar, and **narrow**, with the legend below it. Same items, same numbering, same marker treatments, same key and title block — only the placement of the blocks differs. Neither is derived from the other by CSS; both are laid out by the same code and differ in the translates it applies. |
| **FR-69** | The HTML output embeds **both** arrangements and switches between them with a media query toggling `display`. `display: none` — not `visibility` or `opacity` — is required, because it is what removes the hidden arrangement from the tab order and the accessibility tree; without it every marker and legend row is exposed twice (D-16). The breakpoint value is an implementation detail, tuned to where the wide arrangement stops being legible rather than to any device class; `mockup.html` uses 900px. |
| **FR-70** | In the narrow arrangement the radar is **scaled down within the document**, to the largest factor, at most 1 and at least 0.3, at which its labels fit between the margins; the document widens only when even 0.3 does not fit (D-71). The radar needs roughly 700 user units to hold its quadrant labels; a document that wide renders 12.5px legend text at about 6px on a phone, which fails the legibility SC-6 asserts. Text is authored at its natural size and the radar is scaled to fit around it. Radar-internal labels are counter-scaled so ring and quadrant names survive the reduction. Markers, their numbers and the radar's strokes scale with the radar but **never below 7/9 of their natural size**, so a 9-unit marker number draws at no less than 7 units while the radar's geometry keeps shrinking (D-69). FR-94's hit area is not floored; it is counter-scaled like the labels. |
| **FR-71** | **PNG and SVG export the wide arrangement.** A static image has no viewport to respond to, and the wide arrangement is the one shaped for a slide (G-7). The narrow arrangement exists only inside the HTML output. |

### 6.5 Output formats

| ID | Requirement |
| --- | --- |
| **FR-52** | Output format is inferred from the `-o` file extension — `.html`, `.png`, `.svg` — not a separate flag. Matched case-insensitively, so `.PNG` works. An unrecognised or absent extension is a hard error. |
| **FR-62** | `-o` **overwrites an existing file without prompting** — editions are re-rendered constantly during authoring, and a confirmation prompt would break the non-interactive use the tool is built for. It does **not** create missing parent directories: a mistyped path should fail loudly rather than silently produce a tree nobody meant to make. A missing parent directory is a hard error naming the path. **`-o` naming the input CSV is a hard error** too, compared as files rather than as names, so a typo cannot replace the data the radar was rendered from however the path is spelled (D-74). |
| **FR-53** | **HTML**: the shared SVG embedded in a self-contained file with the full interactive layer (§6.2, §6.4) as inline JS/CSS. |
| **FR-54** | **SVG**: the shared document (FR-44) written directly, no rasterisation. Vector output stays crisp at any zoom or print size and opens in PowerPoint, Figma, and Illustrator for touch-up without the original CSV. |
| **FR-55** | **PNG**: the shared document rasterised via a pure-Rust renderer — [`resvg`](https://github.com/RazrFalcon/resvg) is the library-first choice, avoiding a headless-browser dependency entirely. |
| **FR-56** | `--theme light\|dark`, default `light`, matched case-insensitively via clap's `ignore_case` so `--theme Dark` works (a `theme` from `--config` is matched the same way, FR-91) — the same courtesy FR-52 extends to `.PNG`. **Applies to PNG and SVG only** — both are fixed snapshots with no viewer-side choice, so the tool must resolve colours at generation time. Light is the default as the safer assumption for slide decks and PDFs. **Ignored, not an error, on HTML output**, which carries both palettes and lets the viewer choose via `prefers-color-scheme` plus an in-page toggle: a **Dark theme** button that is pressed while the dark palette shows, follows the viewer's preference until pressed, and appears only when the page's script runs (FR-98's rule). |
| **FR-57** | `--width <pixels>`, default the shared SVG's native width. Height is **always** computed from the SVG's own aspect ratio and is never a second flag — the radar+legend document is not fixed 1:1 (legend height varies with item count and wrapping), so an independent `--height` could silently distort it. Applies to SVG too, where it sets the embedded intrinsic size. **Ignored, not an error, on HTML output.** |
| **FR-64** | `--width` accepts **320–10000** inclusive; anything outside is a hard error, enforced by clap's ranged value parser so the message is standard usage output. A `width` from `--config` is held to the same range with the same message (FR-91). The floor is where the radar stops being legible at all; the ceiling stops a fat-fingered digit turning into a multi-gigabyte rasterisation. Neither bound is a considered aesthetic judgement — they exist so the failure is a usage error rather than an unreadable file or an out-of-memory kill. |
| **FR-58** | **Printing the HTML output directly is not a supported path.** The interactive HTML carries toolbar chrome, a detail panel, and a table toggle that are not meant for paper, and no print stylesheet is specified. PNG or SVG export is the answer for print, slides, and PDFs — that is what they exist for (G-7). |

**Explicitly excluded from this version:** JPEG output (D-17), batch/glob multi-radar rendering (D-18), and auto-computed `status` by diffing editions (D-9). The `status` *column* itself is in scope (FR-26); only its automatic computation is deferred.

### 6.6 CLI

*The tool, the crate, and the command it installs are all **`radargen`** (D-32). Exact flag spelling (`--width` vs `-w`) is settled at implementation planning; what is fixed here is the set of options and their behaviour.*

**No subcommand.** The tool does one thing — one CSV in, one file out — so the input is a positional argument and there is no verb to name (D-28). `--help` and `--version` come from clap and are not enumerated below.

| Argument / flag | Applies to | Default | Meaning |
| --- | --- | --- | --- |
| `<csv-path>` | all | *(required)* | Positional. Path to the input CSV (§6.1). Exactly one; there is no glob or multi-file form (FR-60, D-18). Read errors are fatal (FR-61). |
| `-o, --output <path>` | all | *(required, here or in `--config`)* | Output path; format inferred from the extension (FR-52). Overwrites; does not create parent directories (FR-62). |
| `--title <text>` | all | *(none)* | Rendered above the radar in the shared document. Omitted renders nothing (FR-65). |
| `--subtitle <text>` | all | *(none)* | Second line of the title block — the edition date in practice, though the tool attaches no meaning to it and never supplies one (FR-65, D-24). |
| `--rings "<N1>,<N2>,…"` | all | `Assess,Trial,Adopt,Retire` | Edge-to-centre ordered ring list (FR-12–FR-15). |
| `--theme <light\|dark>` | PNG, SVG | `light` | Resolves the static snapshot's colours at generation time (FR-56). |
| `--width <pixels>` | PNG, SVG | SVG's native width | Sets output width; height auto-computed (FR-57). Range 320–10000 (FR-64). |
| `--palette <file.css>` | all | built-in palette | **Ships (D-44, closing OQ-6).** Overrides the colour roles defined normatively in FR-81 and FR-82 (`--series-1..8`, `--surface-1`, `--text-primary`, and the rest). Format: CSS custom-property declarations, the representation the HTML output already uses internally. **Exactly one set of colours, not a light/dark pair.** **Mutually exclusive with `--theme` — supplying both is a CLI error** (FR-59), since a single-variant palette leaves nothing to choose between. On HTML output, `--palette` means the theme toggle and `prefers-color-scheme` handling are absent from that build. Every role of FR-82 must be present (FR-86) and series entries must be contiguous from `--series-1` (FR-87), with as many entries as the author wants — which is how a radar exceeds FR-83's eight-colour ceiling. Palette **correctness** — contrast, colour-vision-deficiency safety — remains the **user's responsibility**; the tool validates that the file is complete and well-formed, never that its colours are legible. `docs/product/palette.sample.css` ships as the starting point (FR-81). |
| `-c, --config <file.toml>` | all | *(none)* | **v1.1 (D-57).** Reads `output`, `title`, `subtitle`, `rings`, `theme`, `width` and `palette` from a TOML file; a flag on the command line overrides its key (FR-91). Never discovered implicitly. |
| `-e, --edition <YYYY-MM-DD>` | all | *(none)* | **v1.1 (D-58).** The edition's date, which `{edition}` in `output`, `title` or `subtitle` expands to (FR-92). The tool never reads the clock. |

| ID | Requirement |
| --- | --- |
| **FR-60** | The input CSV is a **required positional argument**, and exactly one is accepted. There is no subcommand (D-28), no stdin form, and no way to pass several files. Invoked with no arguments, the tool prints usage and exits non-zero. |
| **FR-59** | `--theme` and `--palette` are mutually exclusive, enforced via clap's `conflicts_with`/`ArgGroup` so the error message is standard usage output, not hand-rolled validation. When either value comes from `--config`, clap cannot see it, so the same rule is checked after the merge and reported with the same wording and exit status (FR-91). |
| **FR-91** | **`-c, --config <file.toml>` supplies flag values from a TOML file.** Its keys are `output`, `title`, `subtitle`, `rings`, `theme`, `width` and `palette`, and each means what its flag means. **A flag given on the command line overrides the same key**, key by key. An empty `--title ""` or `--subtitle ""` overrides with nothing, which is how a config value is suppressed (FR-65). The file is read only when named: nothing is discovered from the working directory or the home directory, because a render must not depend on where it was run (NFR-4). **Values from the file pass the same checks as their flags, with the same messages and exit status**, even though clap never sees them: FR-52, FR-62, FR-63, FR-64, FR-56's case-insensitive `theme`, FR-86, and FR-59's exclusion, which applies across sources and within the file alike. **Types are strict.** `rings` is an array of strings, edge to centre, each entry trimmed as FR-15 trims, so `rings = []` is FR-63's no-rings error; a comma inside an entry is a hard error, because the flag could not express it and the two forms must mean the same. `width` is an integer and the rest are strings. A wrong-typed value, such as `rings = "Adopt,Trial"` or `width = 1920.0`, is a hard error naming the key, and so is **an unknown key**, so a typo like `ring = …` cannot be ignored silently. A duplicate key is a TOML parse error. A file that cannot be read or does not parse is a runtime failure under NFR-15, naming its line where the parser gives one. **Paths in the file (`output`, `palette`):** a relative path resolves against the file's own directory, so a config means the same thing wherever it is invoked from; an absolute path is used as written; `~` is not expanded, since that is the shell's job and no shell reads the file. Paths on the command line resolve against the working directory as usual. **A diagnostic about a value from the file names the key and the file** (NFR-10), and all of a file's problems are reported together (NFR-16 tier one). `-o` is required from one source or the other, and with neither it is a usage error. The CSV is not a key. It stays the one positional argument (FR-60), so the input of a render is always visible in the command. |
| **FR-92** | **`-e, --edition <YYYY-MM-DD>` names the edition being rendered, and `{edition}` in `output`, `title` or `subtitle` expands to it**, whichever source the value came from. The date must be a valid calendar date in that form, or it is a hard error, and it expands exactly as written, so dated filenames sort in date order. **A placeholder is `{`, an ASCII letter, then any ASCII letters, digits or underscores, then `}`, matched case-sensitively**; any other brace is literal text, and placeholders in any other value are literal too. **A value containing `{edition}` with no `--edition` given is a hard error naming the value.** **When placeholders are in use**, meaning `--edition` is given or the value contains `{edition}`, **any other placeholder in it is a hard error naming the placeholder**, so a typo such as `{editon}` is caught rather than published. Otherwise a value such as `--title "Radar {beta}"` renders as written, as it did before this requirement existed, so adding it breaks no working command (NFR-12). **An `--edition` that no value uses is a warning**, because it usually means a placeholder was forgotten; the render proceeds. **Order:** FR-90 removes undisplayable characters first, then `{edition}` expands, then `output` resolves against its source (FR-91), then every other check runs, so FR-52 reads the expanded extension and FR-62 checks the expanded path. The tool still never reads the clock (D-24), so re-rendering an old edition with its own `--edition` reproduces it byte for byte (NFR-4). |

**Three outcomes, not a matrix of interacting flags:** neither flag → built-in light theme; `--theme dark` → built-in dark theme; `--palette <file>` → exactly what the file contains.

```sh
# Today's default radar (the built-in in-house ring set), rendered to HTML
radargen entries.csv -o 2026-09-01.html

# A PNG sized for a slide deck, dark theme, labelled so it stands alone (FR-65)
radargen entries.csv -o 2026-09-01.png --theme dark --width 1920 \
  --title "Technology Radar" --subtitle "Edition 2026-09-01"

# The same edition as an editable vector file, for touch-up in Figma/Illustrator
radargen entries.csv -o 2026-09-01.svg --theme dark

# A different organisation's ring set (the ThoughtWorks convention), same tool.
# Spaces after the commas are fine — each entry is trimmed (FR-15)
radargen entries.csv -o edition.html --rings "Hold, Assess, Trial, Adopt"

# A corporate colour scheme instead of the built-in palette (OQ-6).
# --theme is omitted deliberately: combining the two is a CLI error (FR-59)
radargen entries.csv -o edition.html --palette corporate-palette.css

# A radar's settings kept in a file beside the CSV, so every edition renders
# the same way (FR-91), with the date given once per run (FR-92). radar.toml:
#   output   = "editions/{edition}.html"
#   title    = "Technology Radar"
#   subtitle = "Edition {edition}"
#   rings    = ["Retire", "Adopt", "Trial", "Assess"]
radargen entries.csv -c radar.toml -e 2026-09-01
```

## 7) Non-Functional Requirements

| ID | Requirement |
| --- | --- |
| **NFR-1** | *(stated at §6.4)* WCAG 2.1 AA for the HTML output. |
| **NFR-2** | Single compiled binary. No runtime dependency install — no `node_modules`, no interpreter. |
| **NFR-3** | CLI invocation only (§6.6). |
| **NFR-4** | **Deterministic output, at two strengths.** For **HTML and SVG** — the text formats — the same CSV and flags produce a **byte-identical** file on every run and on every supported platform (NFR-13). For **PNG**, the guarantee is **pixel-identical**: the same decoded image every time, which may differ in bytes between encoder versions. No generation timestamp is embedded (D-19); the output version is, under NFR-12's rule (D-52). All ordering rules are total (FR-10, FR-34) and locale-independent. The split follows the guarantee's own purpose — output is diffable in git across editions — which is a property of text: a binary diff of two PNGs tells a reader nothing either way, so byte-identity there would constrain the build without serving the reason the guarantee exists (D-40). |
| **NFR-17** | **Determinism mechanics**, without which NFR-4 is an aspiration rather than a requirement. **Numbers:** every coordinate and computed value is rounded to **3 decimal places** at emission, half away from zero, formatted with a `.` decimal separator, no exponent, no thousands separator, and no locale involvement. Polar layout means `sin`/`cos`, which are **not** bit-identical across architectures; rounding at emission absorbs that difference, since the discrepancy is on the order of 1e-13 user units and the third decimal place is 1e-3. A value landing exactly on a rounding boundary could still split, which is possible and vanishingly unlikely — accepted rather than engineered around. **Line endings** are **LF** in every text output, on every platform including Windows. **Encoding** is UTF-8 with **no BOM** — the tool strips one on input (FR-2) and never writes one. **PNG:** no encoder settings are pinned and no bit-exactness is claimed, per NFR-4 and D-40. |
| **NFR-18** | **Released as open source under GPL-3.0-or-later**, published to crates.io as `radargen` (D-32) and to a public repository. The copyleft is the point: a modified or redistributed `radargen`, and any program linking it as a library, must ship its own source. **What the licence does not touch is the user's work** — running the tool imposes nothing, and the CSV, the rendered HTML, the PNG and the SVG are the author's alone, since they are the tool's *output* and not derived works of its code. Every crate in the dependency tree is permissive (MIT, Apache-2.0, BSD, Zlib) and so compatible in this direction; GPL-3.0 specifically, because Apache-2.0's patent clause is compatible with GPLv3 and not with GPLv2. The vendored font keeps its own OFL-1.1 terms with its licence text alongside (FR-85) — a font is aggregated with the binary, not a derived work of it. |
| **NFR-19** | **The shipped documentation states the range the tool renders well** — three to six quadrants comfortably, seven or eight busy, beyond eight a sign the categories want revisiting (A-5) — in both the README and `--help`'s description of the input. FR-88 tells an author who has already run it; documentation tells one deciding what to put in the CSV, which is the cheaper moment to find out. The same documentation notes that **a crowded radar is made more readable by raising `--width`, not by the tool growing itself** — output size is the author's lever, and the reason is D-48's. It also states that the **innermost ring has the least room**, roughly a tenth of the outermost, so where the lifecycle allows a choice the sparsest stage belongs at the centre (FR-14) — and it **recommends reading `Adopt` as "we recommend this" rather than "everything we run"** (D-49), with a worked five-ring example — `--rings "Assess,Trial,Adopt,In Use,Retire"` — for organisations that want to track the estate alongside the advice (D-50). All of it is advice about content, which §4 keeps the tool from enforcing: the documentation says what renders well and the author decides. Neither is a constraint: §4 rules out enforcement, and both surfaces say what the tool does rather than what the author should do. |
| **NFR-20** | **Repeated warnings are summarised: one line per warning *class*, enumerating the distinct values that triggered it.** Not one line per row, and not one per value — a single unrecognised-ring line names every undeclared value it saw, each with its count and first line: `41 rows use a ring not declared by --rings — In Use (40, first line 4), Adpot (1, line 37); all appear in the table view`, with the ring set's source worded as FR-17 gives it. **Naming the values is the load-bearing part**, since it is what separates a deliberate `In Use` from a typo'd `Adpot`; a bare count would report that something went unplotted without saying that one of them was a mistake, which is the only actionable half. The same shape serves every class — unrecognised qualifiers, unrecognised statuses, unparsable dates, duplicate names — with values listed in order of first occurrence and **no cap**, because truncating the list would discard exactly the rare value most likely to be the error. A class with no value to enumerate, such as FR-7's empty description or FR-90's removed character, lists its **positions** instead, also uncapped. A class with a single occurrence prints the ordinary per-row message instead. No flag turns any of this on or off: `--quiet` and a targeted `--ignore` were both considered and rejected (D-51). FR-78's table view still carries every unplotted row in full. **Row-level hard errors group by the same rules** (NFR-16 tier two, D-62), **except that every line is listed**, with runs of consecutive lines written as ranges. FR-4's mismatched rows are one class that enumerates each distinct number of values with its row count and its lines — `201 rows have a different number of values from the header's 5 columns, 1 of them unnamed — 4 values (200 rows: lines 2–201), 6 values (1 row: line 202); …`. The line ends with the likely cause of each kind of mismatch present: for fewer values, a missing value or an unquoted line break; for more, a comma that needs the value in double quotes, or trailing empty cells when every value past the header's last column, in every such row, is empty under FR-76; and, first, when no data row matches the header, the header itself. FR-6's empty values are one class **per column** — `3 rows have no value in the ring column — lines 3, 5, 8; every row needs a ring, so fill them in or delete the rows`. FR-4's duplicate headers are not grouped. |
| **NFR-5** | No network access is required to render **or** to view any output. The HTML file makes zero external requests: markup, CSS, JS, and fonts are inlined. |
| **NFR-6** | **All CSV-derived text is escaped for its output context, and the contexts are these five:** (1) **SVG/XML text node** — escape `&`, `<`, `>`; (2) **XML attribute value** — the same plus `"` and `'`; (3) **HTML attribute value** — the same, and never left unquoted; (4) **JavaScript string or JSON island** — JSON-encode, and additionally escape `<` so the sequence `</script>` cannot appear, since **`</script>` terminates the block regardless of HTML entity escaping** and is the one context where the obvious escaping is the wrong escaping; (5) **CSS custom-property value** (`--palette` only) — reject any value containing `;`, `}`, or `<` rather than escaping it, since no safe escaping exists for arbitrary text in a CSS value position. A value crossing into a second context is escaped for **both**, innermost first. Values are emitted as text or data, never as markup, script, or CSS. Characters the output cannot display never reach these contexts: FR-90 removes them on input. A `description` containing `<script>`, `&`, `"`, or `]]>` renders as literal characters. This is a security requirement, not a cosmetic one: output is emailed to clients and opened from disk, and the CSV is authored upstream of this tool. |
| **NFR-7** | **Fonts are pinned, not inherited.** The generator **loads a known font to measure text** (FR-46), the shared SVG declares that same stack explicitly rather than `system-ui`, and PNG rasterisation renders through it — so the same input renders identically regardless of what is installed on the rendering machine. Required for NFR-4 to hold for **every** format, not only PNG: wrap points are computed from real metrics and baked into the HTML, so an unpinned font changes the HTML bytes too. |
| **NFR-8** | **Exit codes.** `0` — render succeeded, with or without warnings. Non-zero — nothing was written. Warnings go to stderr; the rendered file goes to `-o`, never to stdout. |
| **NFR-9** | **Hard errors** (non-zero exit, no output): unreadable or non-UTF-8 input, or a NUL byte (FR-61), a CSV with no header or a non-comma separator (FR-1, FR-3), missing required column (FR-5), empty `name`/`quadrant`/`ring` (FR-6), malformed row or duplicate header (FR-4), unrecognised or absent `-o` extension (FR-52), missing output parent directory or `-o` naming the input (FR-62), an empty/duplicated `--rings` entry (FR-63), an incomplete `--palette` file, a gap in its series or a value that is not `#RRGGBB` (FR-86, FR-87), an unknown or wrong-typed `--config` key, a comma inside a `rings` entry, or no `-o` in either source (FR-91), an `{edition}` with no `--edition`, an unknown placeholder or an invalid `--edition` date (FR-92), `--width` out of range (FR-64), conflicting flags (FR-59), invocation with no arguments at all (FR-60). **Warnings** (exit 0, output written): unrecognised `ring` (FR-17), unrecognised `qualifier` (FR-20), empty `description` (FR-7), unparsable `last_affirmed` or `exit_date` (FR-24, FR-25), unrecognised `status` (FR-26), duplicate `name` (FR-28), a value under an unnamed column (FR-93), a `link` that is not an `http` or `https` address (FR-96), a character the output cannot display (FR-90), quadrant count above six (FR-88), a band holding more items than fit (FR-89), an `--edition` that no value uses (FR-92). **Runtime failures (NFR-15) join the hard-error list**, and NFR-16 governs how many of either are reported per run. The dividing line is consistent: **structure is fatal, content is not** — the tool refuses what it cannot parse or place, and tolerates what it can render but doubts (D-5, D-12, D-27). |
| **NFR-10** | Every warning and error concerning a row names the **1-based CSV line number** and the column it concerns, if it concerns one (FR-4's mismatched number of values concerns the whole row). **That number is the physical line on which the record begins, counting the file's first line as line 1 — the header's line, unless blank records precede it (FR-3)** — not the record's ordinal. The two are equal until a quoted newline appears and diverge permanently afterwards, and the physical line is the one the author's editor can navigate to, which is the whole point of printing it (D-37). **Malformed quoting (NFR-15) is a file-level error, not a row's:** it names the line and column of the fault — where an unclosed quote opened, or where text follows a closing quote — which in a multi-line record can be later than the line the record begins on (D-59). A diagnostic spanning two records — FR-28's duplicate `name` — is reported **at the later line, naming the earlier**, so that NFR-11's ascending order stays well defined. Errors raised before or independently of row parsing — flag validation, output-path problems — name the argument or path instead. **A diagnostic about a configurable setting names its effective source**: the flag, the `--config` key with its file (FR-91), or the built-in default, as FR-17 does for the ring set and FR-90 for a flag value (D-64). A diagnostic concerning the render as a whole (FR-88) names the quantity it reports rather than a line. **A column named by position is given as its 1-based number and its spreadsheet letter**, `column 6 (F)`, since a spreadsheet labels columns by letter and the author would otherwise count across. **Messages say *value* and *column*, never *field*.** **Inside a quoted value, an invisible format character** — any of FR-76's Cf set except U+200C, U+200D and the tag characters, which are content in emoji and joined scripts — **is shown escaped**, `'Ad\u{200b}opt'`, because after FR-76's trim an interior one is the only way a visibly correct value fails to match (D-64). |
| **NFR-11** | Warnings are emitted in **ascending CSV line order**, and within a line in column order as declared by the header. **Row-level hard errors (NFR-16 tier two) follow the same order, whichever stage raised them.** Errors print as one block after the warnings, never interleaved with them. Within a line, an error naming no column position precedes those naming one: on a row's line, FR-4's mismatched number of values; on the header's line, FR-5's missing columns, which then precede FR-4's duplicate headers in column order. Under NFR-20's grouping, of warnings and errors alike, a class sorts by the **first** line it occurs on, and the values enumerated within its line sort the same way, which keeps the order total and independent of hash iteration. Diagnostics are part of the tool's observable output: golden-file tests (SC-8, SC-10) cannot assert against a set that arrives in hash-map order. |
| **NFR-12** | Releases follow [semver](https://semver.org). **Any change that alters rendered output for unchanged input is at least a minor bump**, so a re-rendered edition that diffs can be explained by a version rather than investigated. **HTML and SVG output carry the output version** — `major.minor`, never the patch — as `<meta name="generator" content="radargen 1.2">` in the HTML `<head>` and as the comment `<!-- radargen 1.2 -->` immediately before the SVG root element. The patch is left out because a patch release does not change output, so a full version would make every patch release diff every edition. The line therefore changes exactly when this requirement permits output to change, and a re-rendered edition's diff names the version that explains it. PNG carries none: NFR-4 holds it to pixel identity, where a byte diff explains nothing (D-52). |
| **NFR-13** | **Supported platforms: macOS, Windows, and Linux**, in that order of priority — macOS is where the tool is developed and where the originating radar is published, so it is the platform a regression is caught on first. All three are tier-1 for the byte-identical guarantee of NFR-4 on the formats that carry it. x86-64 and aarch64 both count on each. Named because SC-8 tests output "on a different machine" and §8 cites Windows support when declining qiwi/tech-radar, while nothing in the document said which platforms were in scope. |
| **NFR-14** | **Output is written atomically.** The generator writes to a temporary file in the **same directory** as `-o`, flushes it, and renames it into place — so a failure part-way through leaves any previous file at that path **byte-unchanged**. Without this, NFR-8's promise that a non-zero exit means "nothing was written" is false for any failure after the first byte, and the destroyed file is a published edition (D-37). The same-directory requirement is what makes the rename atomic; a temp file elsewhere risks a cross-filesystem copy that is not. |
| **NFR-15** | **Runtime failures are hard errors** (non-zero exit, nothing written), alongside NFR-9's input and flag errors: output path not writable or naming a directory, no space left, rasterisation failure, font load or measurement failure, a `--palette` or `--config` file that cannot be read or does not parse (FR-91), and a CSV whose quoting is malformed — an unterminated quote, or text after a closing quote, which FR-4's field-count and duplicate-header checks do not cover. NFR-9's taxonomy read as closed while naming no failure that arises from the machine rather than the input, so every one of these had no specified behaviour. |
| **NFR-16** | **Diagnostics are batched in three tiers, not reported one at a time.** (1) **File- and flag-level errors abort immediately** — an unreadable or non-UTF-8 input, or a NUL byte (FR-61), malformed quoting (NFR-15), a CSV with no header or a non-comma separator (FR-1, FR-3), a bad `-o` (FR-52, FR-62, including `-o` naming the input), a malformed `--rings` (FR-63), an out-of-range `--width` (FR-64), conflicting flags (FR-59), a bad `--config` key or value, the file counting as a single flag so all of its problems are reported together, and FR-92's placeholder and date errors (FR-91, FR-92): nothing can be parsed, so there is nothing to collect. Within a single flag, every violation is reported together, as FR-63 already requires. (2) **Row-level hard errors are collected across the whole file** and reported together before exiting non-zero — every missing required column (FR-5) at once, every empty `name`/`quadrant`/`ring` (FR-6), every malformed row (FR-4). They are **grouped under NFR-20** (D-62). (3) **Warnings are collected and reported, then the render proceeds** and exits 0. Fixing a 200-row export one error per run is the failure mode this exists to prevent; FR-5's singular "naming the column" and FR-63's "each violation" had pointed opposite ways, and this resolves them toward collecting (D-37). |

## 9) Decision log

*Decisions from the 2026-08-25 brainstorming session and subsequent reviews, recorded so they don't need re-litigating. Each explains a requirement in §6/§7 rather than restating it. "Added on this review" means the revision in §15 that first names the decision.*

| ID | Decision | Rationale |
| --- | --- | --- |
| **D-1** | **Renderer, not a catalogue.** | A prior Rust CLI + TOML catalogue design (2026-08-09) was rejected for duplicating ArchMan TSR's relational catalogue and decision-linking. Scoping narrowly to rendering avoids reopening that objection. |
| **D-2** | **Stack: Rust.** | Matches the existing cargo-based toolbelt; a single binary over a `node_modules` tree (NFR-2). |
| **D-3** | **CLI parsing: clap.** | Standard, well-maintained, library-first over hand-rolled parsing. Its `conflicts_with`/`ArgGroup` also gives FR-59 a standard usage error for free. *Extended in v0.39:* values from `--config` never pass through clap, so FR-91 re-applies FR-56, FR-59 and FR-64's checks to them after the merge, with clap's wording. |
| **D-4** | **Rings configurable via `--rings`, defaulting to the in-house four.** | Originally specced as hardcoded, on the reasoning that rings carry defined lifecycle semantics and quadrants don't. Revisited once the tool was reframed as a standalone entity. **The default is the lifecycle Assess → Trial → Adopt → Retire, declared edge-to-centre as `Assess,Trial,Adopt,Retire`** (D-60) rather than the more widely published ThoughtWorks set because an in-house radar governs an estate the publisher actually operates: it needs a terminal state with an owner and an exit date (*Retire*, paired with `exit_date`), where an industry-advice radar needs a cautionary one (*Hold*). Neither is more correct in general — they answer different questions — so the tool ships the in-house default and lets `--rings` express the other. *Noted in v0.29, refined in v0.30, and luck rather than design:* the default is also the **geometrically fortunate** one **for the job it is built for**. The innermost band holds about a tenth of the outermost, and an estate radar's `Adopt` — everything currently in service — accumulates monotonically; the default leaves it in the roomier second band from the centre and puts the transient `Retire` at the centre. The ThoughtWorks order inverts that, which is right for **its** semantics, where `Adopt` is a curated recommendation rather than an inventory, and wrong for an estate that borrows the ring names (FR-14). None of this entered the original choice, which was made on the semantics alone — the geometry followed the semantics rather than the other way round, which is the reassuring direction for it to follow. The semantics turned out not to require hardcoding: `qualifier` and `exit_date` were already keyed to whether a value is *populated*, never to a ring's literal name (FR-21, FR-25). What *does* need an explicit mechanism, and doesn't for quadrants, is **order** — a lifecycle progression can't be recovered by sorting names the way alphabetical works for quadrants. Hence an explicit ordered list rather than an inferred one. Omitting the flag reproduces the originating radar's behaviour exactly. |
| **D-5** | **Unknown ring values: tolerated, not rejected** (FR-17). | Teams track things the declared rings have no slot for — `Rejected`, a locally-named retirement state. The CSV and table should hold them even though the graphic can't plot them. A declined or locally-tracked technology is still a decision worth keeping: the catalogue, not the radar, is the authoritative record, so it can legitimately hold states the radar has no band to draw. Failing the render over one would make the graphic's limitations dictate what the catalogue is allowed to record. D-4 governs the *drawing*, not the *parsing*. |
| **D-6** | **`qualifier`: asymmetric fallback, not either/or** (FR-20). | Silently rendering unrecognised input as Conditional would assert a specific, unearned claim — "acceptable only under stated circumstances." Falling back to solid on a row that should have said `default` costs nothing but a warning. *Narrowed in v0.36:* a **blank** qualifier no longer warns — only an unrecognised non-blank value does. FR-21 makes the rule ring-agnostic, so the blank warning could not be confined to the rings where the distinction means anything, and fired mostly on Trial and Assess rows where blank is correct; the PRD's own seven-row example raised it three times. Solid is already the safe fallback, so a blank makes no unearned claim, and FR-26 had reached "blank means nothing was claimed, no warning" for `status` (D-35). A forgotten `conditional` on an adopted item is indistinguishable from a correct blank without checking ring names, which FR-21 rules out — so it is a review-checklist item, not a diagnostic. **Renamed from `adopt_type`** because that name implied a ring literally called "Adopt" was required, when the mechanism never checked the ring's name at all. |
| **D-7** | **Quadrant order: case-insensitive alphabetical, no override** (FR-10). | Originally first-seen CSV order; changed because that isn't stable across editions unless the (still-unspecified) export step emits rows in the same order every time. Otherwise quadrants could visually rotate edition to edition with no underlying change — undermining a published, dated, side-by-side-comparable artefact. Alphabetical is deterministic from the names alone and needs no flag or config file. **Trade-off accepted knowingly:** a deliberately non-alphabetical order (ThoughtWorks' own Tools/Techniques/Platforms/Languages sequence) becomes inexpressible without renaming quadrants. It also means any existing radar whose category order isn't already alphabetical reorders once on migration — for the originating case, `Tool, Platform, Practice` becomes `Platform, Practice, Tool`. A one-time visible consequence, not a bug (see R-4). Rings get the opposite treatment for a reason, not inconsistently: quadrant order is genuinely meaningless, so resolving it automatically costs nothing; ring order is load-bearing and cannot be resolved automatically at all. *Corrected in v0.37:* "genuinely meaningless" overstated it — this entry itself concedes ThoughtWorks' sequence becomes inexpressible, and R-4 books a visible reorder against the originating radar. The reasoning above supports *deriving* the order from the names; it never supported refusing an override, and an explicit `--quadrants` would be exactly as stable, being the mechanism D-4 adopts for rings. The real grounds for shipping without one are smaller and sufficient: no configuration, no new validation or failure modes (what a listed-but-absent or unlisted quadrant does), and **adding the flag later is additive** — a minor bump under NFR-12, with the alphabetical default unchanged for anyone who omits it. So the override is deferred, not rejected (OQ-17). |
| **D-8** | **Near-duplicates not caught** (FR-11). | `Tool` vs `Tools` is a CSV-authoring mistake at a scale where an unexpected extra sector is obvious in the output and fixable at source. Fuzzy matching or a distinct-count warning would solve a problem nobody has hit. |
| **D-9** | **`status` is manual, author-supplied per edition** (FR-26). | Matches BYOR's own convention. Auto-computing it by diffing editions is deferred with no pull-forward request against it. |
| **D-10** | **Case-insensitive matching throughout, with trimming** (FR-76). *Scope widened by D-34 — this decision originally named only `quadrant` and `ring`.* | `Tool`/`tool`, `Adopt`/`ADOPT`, `New`/`new`, `Default`/`default` are the same value. Casing or a stray trailing space shouldn't split one quadrant into two or fail a match a human reads as obviously fine. |
| **D-11** | **BOM stripped on read** (FR-2). | *Added on this review.* Excel emits UTF-8 with BOM by default. Without stripping, the first header parses as `﻿name` and FR-5 fails on a file that looks correct in every editor — a confusing failure with a one-line fix. |
| **D-12** | **Empty `description` warns rather than failing** (FR-7); empty `name`/`quadrant`/`ring` is fatal (FR-6). | *Added on this review, resolving an ambiguity in "every row must have all four."* The first three are structural — without them an item cannot be identified or placed. A description is content: the item still plots correctly, so blocking a whole edition on one missing write-up is disproportionate. |
| **D-13** | **Unparsable dates are rendered verbatim with a warning** (FR-24). | *Added on this review.* Consistent with D-5's tolerance. Nothing computes on these dates in this version, so a malformed one costs only its own display; rejecting the edition over it would be the governance behaviour §4 rules out. |
| **D-14** | **Legend authored in SVG, not HTML/CSS** (FR-44). | Prototyping the legend as a flexbox div was faster; the real tool doesn't inherit that constraint. One SVG document is what makes PNG export cheap instead of requiring a browser engine to rasterise an HTML layout. |
| **D-15** | **`<foreignObject>` ruled out** (FR-47). | It would let the legend stay real HTML — flexbox, native scroll, free text wrap — dodging the wrapping and scroll costs. But `resvg` and other lightweight rasterisers don't support it, because rendering embedded HTML needs exactly the browser-engine dependency choosing `resvg` avoids. It would fix the HTML output and break PNG export, defeating the point of unifying the two. |
| **D-16** | **Two arrangements, one breakpoint: legend beside the radar when there is room, below it when there isn't** (FR-51, FR-68–FR-71). | *Corrected on this review, having been wrong in v0.3 and v0.4.* Those versions claimed that "because radar and legend are one SVG document, side-by-side is not achievable" — and that is simply false. Placing the legend beside the radar in one document is a different translate, the same operation already used to place it below. The real constraint is narrower: **one document means one arrangement, fixed at generation time**, because the generator computes the `viewBox` and `viewBox` is not a CSS property, so a media query can re-arrange nothing — it can only choose between things already drawn. Both costs were then weighed properly for the first time. A side-by-side-only document does not stack on a phone, it *scales*: a ~1200-unit document in a 380px viewport renders at about a third size, and the legend becomes unreadable. A stacked-only document makes a poor slide, which is what G-7 exists for, and R-3's tall-PNG problem is the same complaint from the other end. Emitting both and letting the HTML pick costs roughly twice the graphic's markup in that one format, and `display: none` handles the accessibility duplication for free (FR-69). Rejected alongside: having the HTML re-run layout in JavaScript at view time, which would solve it elegantly and put a second layout implementation in a second language — the divergence D-14 and FR-44 exist to prevent. |

## 10) Risks and assumptions

### What `mockup.html` validates — and what it doesn't

The prototype in this folder is a **layout validation artefact**, not a reference implementation. Reading it as a specification would import decisions it never made.

**It validates:** the polar geometry at 3, 4, and 5 quadrants; equal-width bands at 2, 4, and 5 rings, driven by a ring list rather than a constant (FR-14, FR-32); the divider-at-12-o'clock rule (FR-31); marker distribution within a band (FR-33); a declared ring with no matching rows still drawing its band (FR-19); rows whose ring is outside the declared set leaving the graphic and the numbering while surfacing in the table view (FR-17, FR-18, FR-41); contiguous numbering across plotted items only, assigned in the legend's reading order so a quadrant's numbers ascend as the reader scans down its group (FR-34, D-33); title block and key inside the shared document, and the title reclaiming its space when omitted (FR-65, FR-66); both arrangements and the media-query switch between them (FR-68–FR-70); the legend authored in SVG within one shared document (FR-44); marker↔legend cross-highlighting on hover and focus (FR-37); selection indicated on marker and legend row alike and distinguishable from hover (FR-72, FR-73); the legend's three indented levels and its inline per-row qualifier and status, with the ring kept in the accessible name (FR-35, FR-74, FR-75); keyboard operability and the detail panel's open/close behaviour (FR-38, FR-48, FR-49); and no horizontal page scroll at 390px (FR-51).

**It does not validate, and must not be copied from:** anything requiring real font metrics — it measures text through the browser's Canvas API, which has no Rust equivalent and is the whole of R-1. It escapes its interpolations (NFR-6), but through one HTML-context helper rather than the per-context escaping three output paths need, so it demonstrates the discipline and not the implementation. It has no CSV parser, so none of §6.1's parsing, validation, or diagnostics behaviour is exercised — the datasets are hand-authored JavaScript objects. It renders only to the DOM, so nothing about PNG, SVG, determinism (NFR-4), or font pinning (NFR-7) is tested. It exposes markers and legend rows as controls but **does not meet FR-50**: its markers are labelled `"N. Name"` with no position, and only legend rows carry the ring (FR-75). Nor is its **label placement** to be copied: it centres every quadrant name on the label point, which D-70 replaced.

**It is not the source of truth for anything.** Where the prototype and §§3–7 disagree, the requirement wins and the prototype is simply out of date. Two entries came *from* the prototype rather than the other way round — FR-70 and D-31 exist because stacking the full-width document was visibly illegible on a phone once built — which is what the artefact is for, and not a licence to read layout decisions off it.

### What `palette-proof.html` records

A second artefact sits alongside this document: **`palette-proof.html`**, the verification behind FR-81–FR-83. It shows the eight series colours drawn as the radar draws them on both theme grounds, every contrast ratio against every surface, the four vision simulations, and the prefix-quality table FR-83 summarises.

**It is evidence, not specification.** The normative values are FR-81 and FR-82; the proof sheet exists so that a future change to the palette can be re-argued against the same measurements rather than re-derived from scratch, and so the two rejected alternatives in D-41 stay visible instead of being proposed again. Where it and §§6–7 disagree, the requirement wins — the same rule §10 already applies to `mockup.html`. It is a static page with no build step; open it directly.

**Assumptions**

- **A-1** A catalogue → CSV export step exists and is manual for now (§4). Nothing in this tool depends on how the CSV is produced.
- **A-2** Item counts stay in the tens, not the hundreds, for the foreseeable future — the basis for §4's "manual checking is sufficient" stance. **It does not cover R-3**, which fires at roughly 25 items — inside "the tens", and plausibly within reach of the originating radar, whose legend v0.7 already measured at 14 items.
- **A-3** Readers open the HTML in a current evergreen browser. No IE/legacy support is specified or tested.
- **A-4** Entry text is in a script the pinned font draws — Latin, Latin Extended and Vietnamese, Greek, or Cyrillic (R-7). Nothing warns when it is not. Right-to-left scripts such as Arabic and Hebrew, CJK and the Indic scripts are out of scope: each needs a second font, and right-to-left and CJK also need bidirectional layout or line breaking without spaces (D-68).
- **A-5** **Quadrant counts run three to six in practice**; seven or eight render correctly but read as busy, and beyond eight the **taxonomy is what wants revisiting, not the renderer**. The originating case is three and the ThoughtWorks convention is four, which is the range the geometry is comfortable at: a sector narrows from 120° at N=3 to 45° at N=8 and 30° at N=12, and quadrant labels crowd a single circle with no collision rule (OQ-14). Colour is **not** the first thing to fail — FR-81's eight entries are deliberate headroom so that even the busy end of the range gets distinct colours, not a statement that eight quadrants is fine. The tool renders any N ≥ 1 (G-1, FR-43); above six it says so once (FR-88) and renders anyway.

Recommended **yes**, once (a)–(d) are settled. |

### 14.1 Release slices

Two slices, so BYOR can be retired without waiting for the whole scope (D-30). The boundary is drawn where the *justification* is: SC-1 and SC-2 — replacing BYOR, rendering three quadrants without workarounds — are the criteria that make this project worth doing at all, and HTML alone satisfies both.

| Slice | Contains | Met when |
| --- | --- | --- |
| **v1.0 — replaces BYOR** | The whole CSV contract (§6.1), the layout engine (§6.2), the shared SVG document including title block and key (§6.3), **both arrangements and the switch between them** (FR-68–FR-70), accessibility and responsiveness (§6.4), HTML output, `--rings`, `--title`, `--subtitle`, the HTML output's dual-palette theming (both palettes inlined, `prefers-color-scheme` honoured, in-page toggle) — which is the thing `--theme` is *ignored in favour of* on HTML rather than a behaviour of the flag (FR-56), with `--width` likewise accepted and ignored (FR-57) — the pinned font loaded for text measurement (NFR-7's first half), and the error/warning taxonomy of §7 less `--palette`'s conflict rule (FR-59), which arrives with the flag. | SC-1, SC-2, SC-3, SC-4, SC-5, SC-6, SC-12, SC-13, SC-14, SC-16, and — for the one format it ships, with SC-10 less its FR-59 case — SC-8, SC-9, SC-10, SC-15, SC-25 |
| **v1.1 — the static formats** | PNG and SVG export of the wide arrangement (FR-71), `--width` and `--theme` **taking effect** (FR-56, FR-57), rasterising through that same font (NFR-7's second half), `--palette` with its conflict rule (FR-59) and file validation (FR-86, FR-87), and `--config` and `--edition` (FR-91, FR-92). | SC-7, SC-11, SC-21, SC-26, SC-27, SC-8/SC-9/SC-10/SC-15/SC-25 extended to PNG and SVG, and SC-10's FR-59 case |

`--palette` sits in v1.1 even though it applies to every format, because the argument for it is a PNG argument: HTML colours can be hand-edited in the `<style>` block and an SVG can be recoloured in a design tool, but a rasterised PNG cannot be re-themed at all. Without PNG in the slice, the flag has no case that a text editor doesn't already answer. `--theme` and `--width` are accepted in v1.0 and ignored there, exactly as FR-56 and FR-57 already require them to be on HTML output — so carrying them in a v1.0 invocation is harmless rather than a usage error. A `-o` naming a `.png` or `.svg`, by contrast, fails on a v1.0 binary (FR-52). Its message must say the format is **not supported in this version**, naming the version that adds it — not "unrecognised extension", which sends the caller hunting for a typo in a path that is correct. This is a live UC-1 path, not a hypothetical: the maintainer's documented workflow is one HTML run and one PNG run, so on v1.0 the second half of it fails by design and the message is all that explains why.

**The shared SVG document is built in v1.0, not deferred with the formats it enables.** That looks like carrying cost early — the whole point of FR-44 is cheap PNG export, which v1.0 does not ship. It is deliberate: retrofitting the legend from HTML into SVG afterwards would mean building the legend twice, and D-14 and D-15 are load-bearing enough that discovering a problem with them in v1.1 is far worse than discovering it in v1.0. The text-metrics spike (R-1) therefore stays the first task of the project, not the first task of v1.1.

**What this ordering costs:** UC-3 — the slide deck and the vector touch-up — is unavailable until v1.1, UC-1's "once for HTML and once for PNG" is halved to the HTML step, and G-7 is not met by v1.0. Anyone needing an image in the interim screenshots the HTML, as they do today. That is a real gap, accepted for a bounded period, not a claim that the static formats are optional.
